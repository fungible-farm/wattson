## Authoring effort
- Model language: Python API (`benchmarks/ontology/bsl/model.py`, 106 lines). YAML is supported by the library (`from_yaml`) but its join syntax only takes one `left_on`/`right_on` pair (read in `yaml.py`), so the composite-key price/demand join needs Python.
- Files: `model.py` 106, `runner.py` 121, `chains.py` 45, `gold-specs.json` 115, adapter 105 lines, Containerfile 7, requirements 23.
- Time: about 42 minutes in total, of which the semantic model itself took about 3 minutes plus 9 minutes reading library source. This is a reconstruction from file mtimes, NOT a contemporaneous log (`benchmarks/ontology/bsl/authoring-log.md` says so).
- Model content: 4 semantic models over the 5 tables: `unit_dispatch` (dispatchload joined one-to-one to dudetailsummary on DUID, 16 dimensions, 92 measures), `unit_details` (10 dims, 17 measures), `regional_price_demand` (dispatchprice joined to dispatchregionsum on date+region+intervention, 8 dims, 125 measures), `interconnector_flow` (4 dims, 21 measures). Measures are generated by a loop: avg/min/max (and sum where physical) for every numeric column, row counts and distinct counts on key columns, MWh = MW*5/60 for TOTALCLEARED and AVAILABILITY. `INTERVENTION = 0` is a model-level filter on the facts. No question-specific measure; gold specs were written after the model.

## What cannot be expressed, with the attempts (Python in the image, `--network=none`)
The single JSON spec the model produces (dimensions, measures, filters, order_by, limit) is a one-aggregate contract. BSL's Python API goes further, so I tested before marking anything inexpressible:
- M7 (interval of highest SA1 price, then top unit in that interval):
  - `top.as_scalar()` as a filter: `AttributeError 'SemanticLimit' does not support 'as_scalar()'. Call .to_untagged().as_scalar() to use ibis operations directly.`
  - Scalar subquery through `to_untagged()`: `AttributeError 'Table' object has no attribute 'settlementdate'` (this route is raw Ibis, which bypasses the semantic layer anyway).
  - WORKS: two semantic queries chained by caller code (step 1 `query(... order_by rrp_max desc, limit 1)`, value handed to step 2 as an `=` filter) returns `[['PPCCGT', 406.69696]]`; also an `in` filter with the step-1 value. The hand-off is plain Python glue, so it is expressible with caller orchestration but not as one spec. Gold program `M7` in `chains.py`, Path B correct.
- M8 (share of NSW1 energy from its top five units):
  - `query(measures=...)` on the limited result: `UnknownFieldError Unknown measure ... Declared measures: []`.
  - WORKS inside BSL: `query(duid x energy).mutate(share=...).order_by(desc).limit(5).group_by().aggregate(sum share)` returns 0.4366 (truth 0.437). Raw-Ibis variant also works but bypasses the layer. Gold program `M8`, Path B correct.
- M9 (count of intervals where |sum NETINTERCHANGE| > 50): WORKS in BSL chained API: `query(settlementdate x netinterchange_sum).filter(abs>50).group_by().aggregate(count)` returns 189. The JSON `having` form returns the 189 rows, not their count. Gold program `M9`, correct.
- M4 (intervals where NSW1 price exceeds VIC1 price by more than 10 while VIC1-NSW1 flows forward): NOT TESTED beyond reading the API. It needs a side-by-side pivot of two regions of one table plus the interconnector model joined on time; no such relationship exists in the frozen model and writing one would be question-specific. Recorded as "needs bespoke modelling".
So M7, M8, M9 fail on Path A in the interface layer: the model correctly says (in its `cannot_answer` text) that it needs a sub-query or two steps, because the adapter's contract offers no way to chain. The library itself can do all three (M7 only with Python glue). Whether the adapter contract should expose chaining is a design decision I did not make; it would be a model-producible program language, i.e. new surface.

## Requirement observations
- R1 semantic model as data: PARTIAL. Dimensions, measures, joins live as Python objects (`model.py`) and `json_definition` exports names/descriptions; YAML exists but cannot express the composite join. Evidence: `model.py`, `yaml.py` read.
- R2 binding checks: PASS for names. Unknown dimension/measure raises with suggestions (`UnknownFieldError Unknown dimension 'interconectorid' ... Did you mean: dimension 'interconnectorid'`); typo'd measure lists declared measures; unknown filter field only gives `AttributeError 'Table' object has no attribute 'nonexistent'` and a bad operator `ValueError: Unsupported operator: ~~` (my runner validates these first).
- R3 constraint validation: NOT SHOWN. No data-constraint or SHACL-like API found (grep of the package for constraint/shacl only hit join-cardinality internals); the schema claim "one row per DUID" is declared via `join_one`, not checked (not tested).
- R4 governed path and refusals: PARTIAL. Adversarial 5/6: A1, A2, A4, A5, A6 refused with reasons; A3 ("Which region used the most energy?") was ANSWERED (NSW1 by summed TOTALDEMAND) instead of asking for clarification, a fail. Writes are impossible by construction (read-only DuckDB mount, no write operator in the spec language).
- R5 hints on ambiguity: PARTIAL. Library gives "Did you mean" suggestions on typos; nothing on ambiguous questions (A3 not flagged).
- R6 audit and replay: PASS. Each answer records the JSON spec and the compiled DuckDB SQL (`query` field); rows hash identical across 3 repeats for answered questions; seed sent on every call, temperature 0. Compiled SQL for joined models is large (nested CTEs with `__bsl_jk_` join-key aliases).
- R9 container/offline/arch: PASS. Gate output above: arm64, rootless, `--network=none`, interfaces `lo` only.
- R10 latency: per-answer p50 28.6 s, p95 223 s (model dominated: the generated description is large, 4 models, about 250 field names, so the reasoning model thinks long; M9 hit the 8000 token cap). Per query container start + execution: about 1.5 s for startup, simple query 0.39 s, join query 0.04 s (timed in `probe2`).
- R11 scale: NOT SHOWN. 150k-row dispatchload over parquet in DuckDB only; the prompt grows with every column-by-aggregation measure (92 + 125 measures), which is a context-scale concern.

## Blockers and deviations (exact)
- `just nemosis-fetch` failed first with `exec container process '/bin/sh': Exec format error` because the cached `python:3.12-slim` was amd64 on this aarch64 host; `podman pull --platform linux/arm64 docker.io/library/python:3.12-slim` fixed it (this retags that image locally for everyone on the host).
- The harness ground truth needs `out/nem/nem.duckdb`; `just nem-data` (network download from AEMO, checksum verified) had to be run in the worktree.
- The adapter allows ONE repair call after a validation error (calls=2 on several questions); the baseline has none.
- Adapter prompt text (`HEAD`, plus a one-line note per model) contains domain notes taken from the schema file (negative TOTALCLEARED, MWh formula, NETINTERCHANGE sign, forward flow). The note says "one day: 2025-09-01", which may have encouraged the day filter behind M1/M3/M5.
- Authoring time is reconstructed, not logged.

## Recommendation
BSL is a clean, MIT, small-dependency, offline-capable layer that compiles governed, auditable SQL and refuses writes by construction; the compiled SQL and spec give good audit. Against it: on this development set only 3/10 correct (coverage 0.6, conditional accuracy 0.5); every failure was either the model's own day-boundary filter or the single-spec contract (no chaining), and the model had to be shown ~250 names, which made calls slow. M4-style row-wise comparisons across two groups need bespoke modelling. No constraint validation (R3) and no ambiguity handling (R5). Suitable as the execution layer under a planner that can emit multi-step plans; weak as a drop-in "ask in English, get an answer" ontology.
